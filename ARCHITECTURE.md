## Node devcontainer (walking skeleton)

Proposed design: `.scratch/node-devcontainer/design.md`. Implemented: image, Template, egress start-up step, credential isolation, pnpm policy, extension installer (build and start mode: skills, Claude plugins and hooks, MCP servers with secrets), Consuming Project layer at container start, acceptance suite, CI, Renovate config and weekly rebuild.

| Module | Anchor | Owns |
| --- | --- | --- |
| Base material | `base/` | Files copied to fixed root-owned system paths: `bin/claude-yolo`, `bin/codex-yolo`, `claude/managed-settings.json` (to `/etc/claude-code`), `codex/config.toml` (to `/etc/codex`, lowest layer so yolo flags still win). Host-credential isolation: `vscode/dev-setup-scrub.sh` (to `/etc/profile.d`, hooked into `/etc/bash.bashrc`, run by `postStartCommand`), `git/gitconfig` (to `/etc/dev-setup`, read-only target of `GIT_CONFIG_GLOBAL`), `bin/git-credential-dev-setup` (PAT from `DEV_SETUP_GITHUB_PAT`, github.com only). `egress/` (to `/usr/local/share/egress`): `allowlist.txt` is generated at image build by the installer from the manifests (one domain per line), `start.sh` (root start-up step: locks the Base allowlist, runs `installer install --mode start` on `${DEV_SETUP_WORKSPACE}/.devcontainer/extensions.json` if present, re-locks with the full allowlist; fails closed by `kill -TERM 1` after writing `/run/egress/failed`, writes `/run/egress/ready` on success, and `/run/dev-setup/applied-manifest`, the hash of the project manifest it applied, read by the host skill's `status`), `wait-ready.sh` (the image `postStartCommand` runs it as `node`: `devcontainer up` does not wait for the entrypoint, so this is what makes `up` fail with the reason), `render.sh` (dnsmasq conf + nftables ruleset), `selftest.sh`. Later hardening lands here. `mcp/check-secrets.sh` (to `/usr/local/share/dev-setup`, run by `postStartCommand` as `node`): warns, never fails, for each Named Secret in `/etc/dev-setup/secrets` (`NAME<TAB>declarers` lines) that is unset or empty, naming who declared it (an MCP server, or container-wide). |
| Extension installer | `installer/`, `extensions/base.json`, `variants/node/extensions.json` | Node ESM, no build step; its dependencies are `ajv` and `smol-toml` (exact versions, frozen `pnpm-lock.yaml`; transitive `fast-uri` is held at an older version by `pnpm-workspace.yaml` overrides so every package passes the 7-day release age). Library entry `src/index.mjs` (schema validation, Pinned Ref check, kind x Agent table, fetch-by-SHA, layer merge, allowlist assembly) with a thin `src/cli.mjs` (`install --mode build --manifest FILE...`; `install --mode start` adds `--project FILE` and output-path options such as `--egress-out`). Published schema `extensions.schema.json` (manifests reference it via `$schema`). Every entry kind may carry its own `egress` (the domains it needs); the top-level `egress` is what the layer itself needs; the top-level `secrets` names container-wide Named Secrets (ADR 0004). Build mode copies skills (verbatim, no symlinks, never executed) fetched by exact SHA into `/etc/claude-code/.claude/skills` and `/etc/codex/skills`, and writes `/usr/local/share/egress/allowlist.txt`; the Base Egress Allowlist lives in `extensions/base.json`. Start mode validates all layers together but installs only the project layer, to the same root-owned system paths (container filesystem, no state file: recreating the container is the uninstall; a restart overwrites in place), and writes the full allowlist to `--egress-out`. MCP (`src/mcp.mjs`, dependency `smol-toml`): `mcp` entries are installed with pnpm (exact version, pnpm policy stated by the installer itself) into `/opt/dev-setup/mcp/<name>` at build, or at start for the project layer, and launched as `node <bin>` from there; `mcp-remote` (https `url`, required `egress`, optional `bearerTokenEnv`) has no Pinned Ref. Rendering regenerates from all layers: Claude `/etc/claude-code/managed-mcp.json` (written only when MCP is declared; Claude treats it as exclusive control of MCP servers; `${NAME}` expanded from Claude's env) and a marker-delimited `mcp_servers` block in `/etc/codex/config.toml` (`env_vars`, `bearer_token_env_var`). MCP server names must be unique across layers. Named Secrets (`src/secrets.mjs`): `mergeLayers` unions every layer's top-level `secrets`; both modes write `/etc/dev-setup/secrets` (`--secrets-out`), whether or not MCP is declared, one line per name (never a value) with its declarers (`MCP server "<name>"` from `env`/`bearerTokenEnv`, `container-wide` from the top level; a name may have both). Claude plugins and hooks (`src/claude.mjs`, same `installBuild`/`installStart`): per layer (`image`, `project`) a root-owned `directory` marketplace `dev-setup-<layer>` under `/opt/dev-setup/marketplaces/<layer>` (plugin trees copied from SHA-pinned commits, `pins.json` records each source; a marketplace-referenced plugin is re-pinned and its external source must carry a SHA) and hook scripts under `/opt/dev-setup/hooks/<layer>`. No plugin seed and no `claude` run: Claude reads the directories in place. Build renders `/etc/claude-code/managed-settings.json` from the policy template `/opt/dev-setup/claude-policy.json` (`base/claude/managed-settings.json`: `allowManagedHooksOnly`, `disableSkillShellExecution`, `disableSideloadFlags`, `disableCommandPluginSources`) plus `strictKnownMarketplaces`, `extraKnownMarketplaces`, `enabledPlugins`, `hooks`; start writes the project layer to `managed-settings.d/50-project.json` (Claude unions the strict lists). Codex `plugin` and `hook` are unsupported kinds (D3). Tests: `installer/test/` against local bare-git fixtures (`npm run test:installer`). |
| Node Variant | `variants/node/` | `Dockerfile` (the one place for the base digest and pinned pnpm/Claude Code/Codex versions, also exposed as `io.github.valerid.dev-setup.*.version` labels; `org.opencontainers.image.revision` comes from host env `DEV_SETUP_REVISION` through a `build.args` entry, set by CI and `tests/lib.mjs`); `.devcontainer/features/egress/` is a local Feature carrying only the root `entrypoint` (the devcontainer CLI requires local Features under `.devcontainer/`); `devcontainer.json` is build-time only and becomes the image's `devcontainer.metadata` (`containerUser` root for the entrypoint, `remoteUser` node, `capAdd` NET_ADMIN/NET_RAW/DAC_READ_SEARCH (the last so root can read the manifest in an owner-only project directory), env `DEV_SETUP_WORKSPACE`, `no-new-privileges`, init, env including the pnpm/npm supply-chain policy as `pnpm_config_*`/`NPM_CONFIG_*`, login volumes). |
| Node Template | `templates/node/` | Only what image metadata cannot carry (plus a starter `.devcontainer/extensions.json` with `$schema` and an empty list): `--cap-drop=ALL`, limits, `initializeCommand`, read-only mounts of `.git/hooks`, `.git/config`, `.devcontainer`, `.vscode`. `remoteEnv` passes the PAT (host var named by option `patEnvVar`) and git identity (`GIT_AUTHOR_NAME`/`GIT_AUTHOR_EMAIL`) from the host. Option `image` selects the image. Comment documents adding `remoteEnv` `${localEnv:NAME}` lines for Named Secrets (MCP or container-wide). |
| Acceptance suite | `tests/` | `npm test` (`node --test --test-global-setup=tests/global-setup.mjs`): builds the image, publishes the Template to a throwaway local registry, applies and starts it with the devcontainer CLI, probes as `node`. Harness: `lib.mjs` (build, registry stub, project folders via `projectDir`, `up`/`exec`/`removeProject`) and `global-setup.mjs`, which gives each run an id, a temp root `dev-setup-test-<id>/` for every project folder, a run label `dev-setup.test-run` on the registry stub, a run image tag `dev-setup-node:test-<id>`, and records `HEAD` once for the image revision label. Its teardown removes only what the run owns, pass or fail: containers whose `devcontainer.local_folder` label is under the run root or that carry the run label, the derived `vsc-…-uid` images and volumes of the former, the run tag, the root; no prune, no name guessing. `DEV_SETUP_TEST_KEEP=1` keeps everything and prints it; an image from `DEV_SETUP_TEST_IMAGE` (or the shared default with `DEV_SETUP_TEST_SKIP_BUILD`, the CI path) is never removed. `cleanup.test.mjs` runs `fixtures/harness-probe.mjs` in child runs to prove this. `acceptance.test.mjs` covers the base container (Template apply, hardening, Agent pins and modes, image labels). `mcp.test.mjs` covers MCP servers and secrets (stdio server via the registry stub and installer start mode, Agents' listings, secret in server env, no value in layers/files/repo, missing-secret warning through a real `up`). `credentials.test.mjs` covers host-credential isolation with fake tokens; manual VS Code checklist in `docs/manual/vscode-reopen-in-container.md`. `extensions.test.mjs` derives throwaway images from the built one and runs the installer there against a fixture repo (skill visible to Claude via its init event and to Codex via its model request). `project-layer.test.mjs` covers the project layer (skill and egress domain appear on recreate, are root-owned and read-only, vanish on removal; an invalid manifest fails `up` naming the entry) with a local bare-git fixture mounted at `/fixtures` and `DEV_SETUP_GIT_BASE` (test seam read by `start.sh`). `pnpm-policy.test.mjs` runs pnpm in fixture projects against `fixtures/registry-stub.mjs`, a dependency-free registry stub on container loopback with controlled publish times. `plugins.test.mjs` covers Claude plugins and hooks (init event, SHA pins, other marketplaces refused, repo `.claude/settings.json` hook ignored, project add/remove). `dev-container-skill.test.mjs` runs the skill helper against a real container (`status` included). `pins.test.mjs` and `renovate.test.mjs` check the pin rules and Renovate managers against the repo files. |
| CI/release | `.github/workflows/ci.yml` (also a weekly `schedule`), `scripts/check-pins.mjs`, `renovate.json` (native managers plus custom regex managers for Dockerfile/workflow version pins, the cosign pin in `skills/dev-container/scripts/commands.mjs` and manifest `sha` Pinned Refs; 7-day npm release age; never auto-merge) | PR checks: pin check (`scripts/check-pins.mjs`, `tests/pins.test.mjs`), installer and skill-helper tests, acceptance run (`npm test`) against the CI-built image; on `main`: build and push, cosign keyless sign, SBOM and provenance attestations (pushed to the registry), Template publish with the `image` option default rewritten to the digest. |

Egress: the start-up step consumes an allowlist file (override with env `EGRESS_ALLOWLIST`) and knows nothing of manifests; the installer emits that file. Test seam: `tests/` probes as `node` and asserts the container stopped on a broken allowlist.

Dependency direction: Template references the image; the image never references the Template; tests depend on everything.

## dev-container host skill

Proposed design: `.scratch/dev-container-skill/design.md`. Implemented so far: onboarding (verified image digest), Presets (adopt, remove, save, edit), migrate, verified image updates, egress domains and secrets (allow/disallow, add/remove), add/remove single Agent Extensions after review, status and Preset resync.

| Module | Anchor | Owns |
| --- | --- | --- |
| Skill prompt | `skills/dev-container/SKILL.md`, `references/<operation>.md` (onboard, migrate, update, presets, egress-and-secrets, extensions, status: rendering and Preset resync) | Conversation: routing, confirmation points, guardrails (only `verify-image` digests are written, no commits, secret values never asked for, read or written, `docs/agents/` and `.scratch/` left alone, `/setup-matt-pocock-skills` only reminded). Installed by symlinking the folder into `~/.claude/skills`. |
| Skill helper | `skills/dev-container/scripts/` | Node ESM CLI, JSON on stdout. `dev-container.mjs` checks the checkout found through its real path (and the `~/.claude/skills/dev-container` link) before anything else, exit 3 = re-link. `commands.mjs`: `variants`, `resolve-target`, `image-digest` (`docker buildx imagetools`, unverified, not used by the flows), `verify-image` (cosign signature + provenance in a pinned container, identity `ci.yml` on `main`; fails closed; then image labels and, with `--current`, the change summary), `render-template` (fills `${templateOption:…}` from the local `templates/<variant>/`, adds an empty Extension Manifest; `--replace` deletes an existing `.devcontainer/` first, for migrate), `validate` (`jsonc-parser` + installer `validateManifest` and `mergeLayers`; counts `preset` tags; checks each Named Secret of the project manifest, on an MCP entry or in the top-level `secrets` (`container-wide`), has a `remoteEnv` `${localEnv:…}` reference, one result per name with all its declarers), `presets` (lists and checks `presets/*.json`, refusing a top-level `egress` or `secrets`), `plan-remove-preset` and `plan-remove` (read-only removal plans computed from the manifest alone, nothing fetched: the tagged entries or the one entry, their own egress domains, each with the staying entry or top-level egress that still allows it, and their Named Secrets, each with what still declares it and whether its `remoteEnv` line stays (it goes only with the last declaration); the top-level `egress` and `secrets` are never part of a removal), `plan-disallow` (read-only: the domain leaves the top-level egress, or a refusal naming each needer among the three layers, Base and Variant read from the pinned image, an entry, or a parent domain; layers unknown is a note, not a refusal) and `plan-remove-secret` (read-only, names only: a container-wide secret leaves the top-level `secrets` with its `remoteEnv` line unless a Base or Variant layer declares it too, and the host variable the user may unset; refused while an MCP entry declares it), `vscode-settings`, `up`, `first-lockfile`, `import-lockfile`, `frozen-install` (all four through the devcontainer CLI via `npx`, same pin as `tests/lib.mjs`; pnpm runs only in the container). Only `render-template` (into `.devcontainer/`) and the lockfile commands (`pnpm-lock.yaml`, `package.json`, the converted lockfile, through the container) write project files. `manifests.mjs`: shared read-only manifest and Preset reading and pure coverage (`readProjectManifest`, `listPresets`, `egressNeededBy`, `egressGoing`, `secretsNeededBy`, `secretsGoing`, `readJsonc`, `readRemoteEnv`, `localEnvName`; across layers `egressDeclarations`, `egressCoverage`, `allowing` and `secretDeclarations`, all matching subdomains with `covers`). `image-layers.mjs`: `readImageLayers` reads the Base and Variant manifests (`/opt/dev-setup/manifests/*.json`) out of the image the project pins with `docker create --pull never` + `docker cp` + `docker rm -v`, never starting or pulling it; "unknown" with a reason when the image is not local; never falls back to the checkout. `projectLayers` gives a project's known layers plus its own manifest, for `status`, `inspect`, `plan-disallow` and `plan-remove-secret`. `inspect.mjs`: `inspect` (resolve a Pinned Ref, fetch with the installer's `fetchBySha`, inventory the content read-only, propose or refuse the entry through installer validation, with the hosts the content certainly reaches on the entry's `egress`; git, `npm:` and `https://` MCP sources; with `--project`, `allowedBy` covers all three layers, `project.layers` says whether the image layers were read). It runs nothing from, or inside, a fetched tree. `status.mjs`: `status` (read-only; builds on `validate` and `verify-image`, which `commands.mjs` hands it; Preset drift per entry (egress included) with exact `resync` entries, Pinned Ref ages, `layers` (read from the image or unknown), every egress domain of the three layers with its layer, needer and covering parent domains, `--domain` for whether one host is already allowed (the "allow" flow), Named Secrets of all three layers and unset host variables by name only (the PAT host variable behind remoteEnv's `DEV_SETUP_GITHUB_PAT` line as a note, `env.pat`, not in `missing`), and a pending recreate for the container found by its `devcontainer.local_folder` label, from the applied-manifest hash, image and `remoteEnv`). Test seam `DEV_SETUP_GIT_BASE`. No subcommand accepts a secret value. Own `package.json`/lockfile (`jsonc-parser` exact). Tests: `scripts/test/` (`npm run test:skill`), `tests/dev-container-skill.test.mjs` (also `status` against a real container), manual `docs/manual/dev-container-skill-checklist.md`. |
| Variant metadata | `variants/<name>/variant.json` | Description and detection files, read by `variants`. |
| Presets | `presets/<name>.json` | Extension Manifests with a required `description`, entries untagged, egress only on entries and secrets only on MCP entries (a top-level `egress` or `secrets` is refused by `presets`). Copied into projects with a `preset` tag on each entry (ADR 0005; both fields are optional in the installer schema and ignored by the installer). Read by `presets`, written by the agent. No example Preset yet; format in `presets/README.md`. |

Dependency direction: prompt → helper → installer library (relative import) and repository data. The installer and images never reference the skill.
