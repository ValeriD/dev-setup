# Quarterdeck architecture

Module anchors and durable decisions are indexed in [ARCHITECTURE.md](../../ARCHITECTURE.md#quarterdeck). This page describes shipped mechanisms, not completion of the real-agent acceptance runs.

## Dependency flow

```text
host quarterdeck → Quarterdeck image → Base material + extension installer
mate skills → FirstMate commands → claude launcher → docker exec → project container
qd-project skill → qd-project-new / qd-project-rm → Project folder, config record
Second Mate or First Mate skill → qd-project-up → devcontainer CLI → socket proxy → Docker
publish Crewmate → qd-publish → git + gh → GitHub
```

FirstMate owns session lifecycle and supervision; Quarterdeck supplies configuration, managed skills and the launcher on PATH, not a replacement lifecycle wrapper. The owning Second Mate dispatches Crewmates for a GitHub Project; the First Mate dispatches them for a Project with no remote, which stays in its own home. The skills preserve generated Brief safety and delivery-contract lines while editing private Brief content.

## Startup and home ownership

The host command builds a missing image and mounts the host work root at the same absolute path. The pool is additionally mounted at `/home/node/.treehouse`; Claude state lives under the work root. Host-created folders and the token file must be usable by container uid 1000. Git author/committer identity is passed at container creation: host variables win, unset or empty ones are filled from the host's `git config user.name`/`user.email`, and any still missing is warned about by name.

The host checks token-file ownership, warns on mode other than 0600, and mounts it read-only. `qd-entry` applies Base egress against the image's empty workspace, checks readiness, then starts `qd-server` and `qd-first-mate` as `node`. The server parses declared secret names without shell evaluation and supplies them to Herdr's environment. It also sets `SHELL=/bin/bash`, so Herdr panes run interactive bash; `/etc/quarterdeck-shell.sh` (from `quarterdeck/shell-profile.sh`, sourced by `/etc/bash.bashrc` and `~/.bashrc`) gives panes one shared in-container history (`/home/node/.bash_history`, gone at `quarterdeck stop`) and `less -FRX` as pager (ticket 30, decisions 100-102). An interactive `docker exec` bash shell sources the same profile; it has the shared history but no tokens. **Environment delivery is not file isolation:** the mounted source remains readable to the same UID from an outside exec shell. [Ticket 21](../../.scratch/quarterdeck/issues/21-mvp-security-review-decisions.md) decision 2 accepts this and narrows SC-19 to no inherited token variables in that shell (security concern 07 is closed by that acceptance).

The First Mate home is copied from the root-owned, full-history pinned checkout, avoiding Git's ownership refusal on a local clone. An existing shallow home is unshallowed from that image checkout using file-only Git transport, without replacing its HEAD, index or working files. Only missing shipped configuration files are added on subsequent starts. Setup writes onboarding/trust state; `qd-first-mate --seed-only` stops there. Normal startup then opens one `firstmate` workspace running Claude Opus in auto mode. The shipped configuration selects Herdr, Sonnet for Second Mates, shared-quota dispatch with Opus for skills/prompts/agent-tool tickets and Sonnet otherwise. Typed dispatch remains off.

`quarterdeck start --no-first-mate` starts the container, proxy and Herdr without attaching, creating the First Mate workspace or launching Claude. It waits for completed home setup, egress readiness, Docker answering and Herdr running. A later normal `start` or attach opens the skipped First Mate workspace in the same container. Agent-free start refuses an existing First Mate workspace rather than stopping sessions. Normal startup readiness includes workspace creation; it does not prove Claude completed an unattended turn. The container lifetime follows Herdr's server. Restarting does not implement Spec Run recovery.

The default Docker bridge avoids embedded-DNS rules being removed by Base's ruleset flush. The proxy uses a shared Unix socket, so it needs no Base egress change. Ownership labels are placed on containers, not the image; proxy resources have a separate label key. Host stop removes its labelled Quarterdeck/proxy containers and proxy volume, not project containers. Endpoint filtering does not inspect container-create bodies or restrict their host mounts.

## Project execution and publication

[Project-container documentation](../../quarterdeck/PROJECT-CONTAINERS.md) owns the renderer's accepted `runArgs`, retained Features, mount set, creation-time extensions-token exception, reuse identity, launcher environment and private publish marker. Those mechanisms are not a general isolation guarantee.

The publisher uses the clone's explicit Git directory rather than a worktree's redirectable `.git` file. It forces hooks and fsmonitor off through environment and command-line overrides and pushes with `--no-verify`. It derives the PR body from numbered ticket titles on the branch and the base branch from origin. These controls do not neutralize every Git configuration key or shared-store attack; the index links the accepted Git-redirection decision. A successful push followed by failed PR creation is a partial result, not an automatically retried transaction.

## Errands

An Errand is one FirstMate record: one job, one branch `fm/<id>`, one pool worktree, one Crewmate. The `qd-errand` skill asks its questions first, writes the Brief ([`references/brief.md`](../../quarterdeck/skills/qd-errand/references/brief.md)) and dispatches with FirstMate's own commands. Quarterdeck adds no store, retry or wrapper.

**Project with no remote** (`qd-project` creates it with `qd-project-new`, registers it `local-only` with yolo off, and `qd-project-up` starts its container from the recorded config tree). The First Mate dispatches the Errand; the launcher routes the Crewmate into that Project's container; the Crewmate commits on its branch, ends with `check: passed`, `check: failed` or `check: none` (from `.quarterdeck/errand-check.md` on `main`, if any), and the First Mate relays a short report. There is no captain hold: the Quarterdeck image has no `tasks-axi`, so `fm-captain-hold.sh` cannot run, and the user's explicit word is the whole approval. On that word, and only for a ready report, the skill runs `fm-merge-local.sh`, which fast-forwards `main` and refuses a dirty main folder, a moved `main` or a changed head; nothing is forced. The Project's main folder is not mounted into its container, so the user's files stay untouched while Errands run.

A question stops the Crewmate with a `needs-decision` line; the answer, or a send-back before any `done`, is `fm-control.sh relaunch --note` in the same worktree. Revised work after a `done` is a **follow-up Errand** with a new task id and a branch from today's `main` that brings the old branch's commits over; the old task stays open until the follow-up lands, then closes with `fm-teardown.sh --force`, which deletes its branch (the user is told first). A dead Crewmate shows only in `fm-send.sh`'s "has exited" notice, not in `fm-crew-state.sh`. Accepted risks: [ADR 0011](../adr/0011-accept-shared-state-and-ref-risks-for-errands.md).

**Project on GitHub.** The First Mate hands the Errand to the Project's Second Mate, which runs it as its own FirstMate record beside any Spec Run record in the existing container, then publishes through the private route and `qd-publish --body-from-brief`. The First Mate merges nothing. A revision after the pull request opens is a new Errand.

## Validation boundaries

[Quarterdeck tests](../../tests/quarterdeck.test.mjs) cover plumbing, structural skill contracts and token-free loops with the [Crewmate fixture](../../tests/fixtures/quarterdeck-crewmate/). The loop uses normally seeded full-history homes, real FirstMate/Herdr commands, simulated Stop hooks and a local origin. An offline migration fixture checks shallow-home repair against the root-owned image checkout while preserving local commits, staged/unstaged changes and home files. Agent-free startup coverage uses a stub Claude and exercises later normal activation. The mates' read access to the managed skills folder is checked by running the image's real Claude Code against a [fake Messages endpoint](../../tests/fixtures/claude-mock-server.mjs) with a dummy key: it records Claude's own permission decision for one tool call, with no login and no model.

The shipped Spec Run skill specifies planning, ordered fresh ticket sessions, one failure retry, question/death stops and a correlated report. Real unattended planning, supervision, publication, attention marks and failure-path runs remain unproven; dependency ticket 18 is still awaiting real-agent evidence. The manual checklist linked from the index owns those procedures and their prerequisites, including a real Crewmate's busy and turn-end signals through the opt-in hook. `qd-project-up` adds that hook only to containers it creates (ticket 15, see the project-container documentation); the fixture checks the installed managed hook and runs it against FirstMate's real `fm-busy-event.sh`. Herdr's own status dot does not read FirstMate's busy state.

The pinned devcontainer CLI copies the allowed creation-time extensions token into the project container's `/etc/environment`. [Ticket 21](../../.scratch/quarterdeck/issues/21-mvp-security-review-decisions.md) decision 1 accepts this until the Git gate ([ADR 0010](../adr/0010-read-only-agent-extensions-token.md)); the tested requirement is that the token appears in no rendered config, work-root export, log or image layer. Ticket 21 also accepts trusted Features (decision 3), clone Git credentials (decision 4) and publish-session influence and worktree redirection (decision 5) for the MVP. Details live in the project-container documentation. `qd-project-up` takes `.devcontainer/` from the repository's default branch as origin reports it (`main` or `master`; ticket 24), and fails before creating anything when origin reports none. Real-token permission scope (security review 04) and real-Claude publish instruction loading remain manual checks.

**Errands evidence.** `npm run test:errands` ([tests](../../tests/errands.test.mjs), [stub Crewmate](../../tests/fixtures/errands-crewmate/claude.mjs)) proves token-free, with real FirstMate commands: the Markdown Variant build, record and hardening; `qd-project-new` and the no-remote `qd-project-up` path (config from the record after `main` moves, unlisted image refused); `qd-project-rm`; launcher routing for two Projects; dispatch into the Project container with the main folder unchanged; the check line; accept and its refusals; questions, a killed Crewmate, relaunch, the follow-up Errand and both teardowns; two Errands at once; and a GitHub Project Errand with a local origin and stub `gh`, with no GitHub credential in the container. `tests/quarterdeck.test.mjs` checks the skills' structure (every command they name exists) and the `qd-publish` flag. Proven only by the manual checklist with a real Claude ([Errands 07 rows](../../quarterdeck/CHECKLIST.md)), none yet run: the skills' behaviour (questions before dispatch and none after, the report, the attention mark, "what is waiting") and a real GitHub Errand. The `qd-project` config-update step has no test of its own.
