# Quarterdeck-created project containers

Run `qd-project-up <home> <project>` as `node` inside the Quarterdeck. The home must be under `QD_WORK_ROOT`; its clone is `projects/<project>`. Success prints the container ID after `wait-ready`. The command asks origin for its default branch (`main` or `master`; it fails before creating anything when origin reports none) and fetches that branch explicitly; local edits and other branches do not select configuration. **MVP operating rule (ticket 21): only start Projects whose default branch you control.** Features and retained configuration from that branch are trusted input. Other repositories wait for the custom socket proxy; unsupported `runArgs` remain rejected.

The export lives under `quarterdeck/config/<project>/<home-hash>/<tree-hash>/`. The home discriminator prevents rendered mounts colliding between homes. Only regular files are exported; symlinks and submodules fail closed. The renderer replaces `devcontainer.json`, keeps the image and Features, allows only `--cap-drop=ALL`, positive memory limits and positive PID limits, and always supplies capability-drop. It drops project lifecycle commands and `remoteEnv`. The exported `.devcontainer/extensions.json` is the committed one (or an empty manifest) plus the Quarterdeck-added entries from `quarterdeck/project-layer.json`, which join the Consuming Project's Extension Layer of that container only: FirstMate's Crewmate busy and turn-end hook as one `hook` entry per event (ticket 15). The start-up installer installs them like any project-layer hook, as managed hooks, so the hardened policy (`allowManagedHooksOnly`) stays. The script, `quarterdeck/hooks/crewmate-busy.sh`, is pinned by commit, does nothing without `FM_TASK_ID` and `FM_TASK_INBOX`, binds each Claude session to the generation armed when it first fires (read as data, so a session that outlives a relaunch is refused, as FirstMate's own wiring refuses it), and runs only `fm-busy-event.sh` from the read-only `<home>/bin` mount. Base, the Variant, Templates and a hand-opened container are unchanged. Non-secret `containerEnv` values must be literal strings. GitHub, GH_, token, secret, password and credential names are excluded. These name checks cannot identify arbitrary literal secrets under innocuous names.

The devcontainer CLI inherits neither the pane's general environment nor its home/configuration. It runs with a temporary empty home, fixed PATH and the Docker socket address. The sole credential exception is `QUARTERDECK_EXTENSIONS_TOKEN`, supplied to the creation CLI as `DEV_SETUP_GITHUB_PAT` and passed by name via `-e DEV_SETUP_GITHUB_PAT`, never written into the rendered config. It must be a fine-grained read-only token for `ValeriD/skills` only (ADR 0010). Base's helper makes it available at startup for fetching Agent Extensions. Missing or empty input warns by name and does not prevent creation; a private fetch still fails through the existing installer. No launcher forwarding is added. Its value is visible in project-container `docker inspect`, an accepted MVP trade-off, not a permission check. Ticket 21 explicitly accepts the pinned CLI's copy in the project container's `/etc/environment` until the Git gate replaces delivery. The narrowed no-file requirement covers rendered configuration, work-root exports, logs and images, not files inside the project container. Review 05 is resolved by acceptance; real permission/startup evidence remains the human's check in review 04. Features still execute during image construction and can supply runtime metadata; this is **not** a complete sandbox or a proof that arbitrary Features preserve the mount set, egress, or credential exclusion. The trusted-default-branch acceptance is recorded in `.scratch/quarterdeck-security-review/issues/01-project-config-trust-boundary.md`, not a claim of Feature isolation. The fixture proves the ordinary Template and a benign local Feature, not arbitrary project input.

Containers are selected by creator, project and canonical home labels (plus `QD_RUN_LABEL`, if supplied). The tree hash and the `quarterdeck.layer` digest of the Quarterdeck-added entries control replacement. Stopped matching containers are started again. Token changes (including unset → set or removal) do not change that identity: to apply them, first verify the exact container's creator/home/project labels, remove that container, then rerun `qd-project-up` from a Herdr pane with the intended environment. Revoke compromised tokens at GitHub; removing a variable does not revoke a reused container's credential. Replacement removes containers, not named Claude/Codex volumes or old exports: those may contain session state and are not pruned. Concurrent calls for one home are unsupported in the MVP's sequential Spec Run model.

All bind sources are prepared as the invoking user. The host work root must map to the same path in Docker and be writable by uid 1000, as required by `quarterdeck`. The pool uses the host `QD_WORK_ROOT/pool` source and `/home/node/.treehouse` destination in both containers.

## Projects with no remote

`qd-project-new <name> <variant> [preset…]` (as `node`, in the Quarterdeck; `QD_WORK_ROOT` set) creates `<First Mate home>/projects/<name>` (the home is `QD_FIRST_MATE_HOME`, default `<work root>/fleet/firstmate`) as a git repository with no remote. Its first commit on `main` holds `.devcontainer/` from the Variant's Template (baked into the image under `/opt/qd/templates`), with `${templateOption:image}` filled from the image id in `<work root>/quarterdeck/local-variants` and `patEnvVar` left at its default, and the named Presets (`/opt/qd/presets`) copied into `extensions.json`, each entry tagged with its Preset (ADR 0005). It writes the git tree id of that `.devcontainer/` to `<work root>/quarterdeck/local-projects/<name>` and links `<work root>/projects/<name>` to the folder. An existing name (folder, record or link), an unknown Variant, an unbuilt Variant or an unknown Preset is refused before anything is created. It registers nothing in FirstMate and starts nothing.

`qd-project-rm <name>` (as `node`, in the Quarterdeck; `QD_WORK_ROOT` set, home as for `qd-project-new`) removes what the Quarterdeck made for one Project: the container labelled with creator `qd-project-up`, that home and that Project (all three labels, no name pattern, no volumes), the exports under `<work root>/quarterdeck/config/<name>/<home hash>`, the `<work root>/projects/<name>` link if it is a symlink to the Project's folder, and finally the config record. It refuses, changing nothing, while any `<home>/state/*.meta` FirstMate record has `project=` naming the Project (there is no force option), and for a name with no container, exports or record. A Project container can write `state/`, so a Crewmate could delete its own record and defeat the refusal; the user's confirmation in the `qd-project` skill is the other guard. The folder, its git repository and the FirstMate registry entry are never touched: the skill removes them after this succeeds.

With no `origin` remote, `qd-project-up` skips the fetch and renders the recorded tree, not `main`: a Project container can write its own git store and so move `main`, but no Project container mounts the record. Objects are checked by hash, and `GIT_NO_REPLACE_OBJECTS` is set so replace refs cannot substitute the tree. A Project with no remote and no record is refused; it never falls back to `main`. Only an explicit, user-requested update through the `qd-project` skill replaces the record. A Project with an `origin` remote is unchanged. The record is only as trusted as the work root, which mates can write (accepted in the design).

## Claude launches

FirstMate invokes `/opt/qd/bin/claude` through PATH. From a directory below `/home/node/.treehouse`, it resolves the home from `FM_TASK_INBOX=<home>/state/<id>.inbox` and normally requires exactly one running `qd-project-up` container labelled for that canonical home and, when the id has a brief, for the Project the brief names. The Project is read from `<home>/data/<id>/brief.md` (FirstMate's `fm-brief.sh` writes "a disposable git worktree of <project>"); Project containers mount `state/` but not `data/`, so neither they nor anything in `state/` or the worktree can change it. An id with no brief (a Second Mate's single-Project home) is routed by home alone, so a home with several Projects and no brief fails as ambiguous. Run the creator first; missing/ambiguous containers fail rather than launching locally. The pool root itself is refused. Other directories exec `/usr/local/bin/claude` unchanged.

For publication, the owning Second Mate writes `<home>/data/<id>/qd-route` and relaunches the same record. The launcher derives both home and id from the inbox path, consumes that marker, and execs the real Claude in the Quarterdeck with `HERDR_AGENT=claude` and appended `--setting-sources user`. It appends hooks-off/fsmonitor-off Git environment entries after FirstMate's entries. Markers in project-writable `state/` or the worktree do not select this route. The ordinary fixture cannot write `data/`; arbitrary Features/shared Git behavior are not proven isolated. The settings flag's real instruction/skill-loading behavior remains a checklist item, not a security blocker: ticket 21 accepts publish-session influence as the misled-mate risk, bounded by the repository-scoped token until the hardening pair/Git gate. Shared clone Git configuration can already contain readable credentials (accepted until the post-MVP hardening refusal check); worktree Git redirection is also accepted, not isolated by read-only overlays.

Before project launches, a `node -e` exec as `node`, serialised by `flock` on `$CLAUDE_CONFIG_DIR/.qd-trust.lock` so overlapping launches keep each other's entries, merges exact-directory trust into the container's own `$CLAUDE_CONFIG_DIR/.claude.json`. Missing/empty files get onboarding completed; existing valid content is retained, and malformed content fails without replacement. The Quarterdeck's config is untouched. Claude runs interactively as `node`, with the original argv and working directory. The Docker process carries `HERDR_AGENT=claude`. Only the ticket's allowlisted environment names cross; no GitHub variable crosses through this launcher. This does not remove creation-time credentials or establish isolation from shared mounts/Features described above.

The host command passes `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME`, and `GIT_COMMITTER_EMAIL` at Quarterdeck creation; each one unset or empty on the host is filled from the host's `git config user.name` or `user.email` (only those two values are read), and any still missing is warned about by name at start. Restart it to change those values. JSONL records in `<work root>/quarterdeck/logs/launch.log` contain route, container, cwd and model only, not full prompts or environment values. Real Herdr state and Claude prompt behavior still require `CHECKLIST.md` validation.

Test-only seam: `QD_PROJECT_TEST_IMAGE=<exact image name>` permits that one locally built image instead of a published `ghcr.io/valerid/dev-setup/<variant>@sha256:…` image, and only in a Quarterdeck the test suite started: `qd-entry` writes the root-owned marker `/run/quarterdeck-test-run` when the host command was given `QUARTERDECK_RUN_LABEL`. In a normally started Quarterdeck the variable is ignored, whoever sets it. `QD_RUN_LABEL=key=value` propagates the host command's test-run label. No registry egress additions were needed for the local Feature fixture; remote Feature registries remain unvalidated.
